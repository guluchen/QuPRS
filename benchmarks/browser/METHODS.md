# Browser timing interpretation

The native comparator in this screen is the **same browser adapter compiled natively**, not the unmodified upstream CLI. Both native and WASM capture the counter request, run the original GPMC, and replay the upstream verifier to consume its result. This controls the mathematical pipeline when measuring browser overhead, but includes adapter replay and input-transport overhead on both sides. It must not be presented as the overhead against a single-pass stock QuPRS CLI.

This fork starts at the current upstream Rust v0.16.0 revision 0b287366. The earlier PathsumWMC direct comparison used the paper-era Python revision 60bcb250 and its original counter. Their times are separate experiments and are not interchangeable baselines. Input circuit pairs for the current screen are the original 73 paper-era pairs, verified by all supplied SHA256 values.

Every selected mode/input receives both adapter profiles on the same pinned CPU, serially with rotated ordering. The common whole-request cap is 200 seconds. Only a first successful whole request below 2 seconds earns four additional trials; longer successes and failures remain single-trial screens. No timeout or failed cell is assigned an artificial time. A completed numerical report is distinct from a finite displayed distance and from a rigorous certificate. RR approximate acceptance can legitimately have no displayed distance.

Native processes inherit a 4 GiB address-space limit and a 16 MiB stack. Each browser WASM module is capped at 512 MiB of linear memory; this does not cap the combined Chromium process. Memory failures and timeouts remain in the coverage denominators. A browser failure at its smaller cap is not proof that the native algorithm is incorrect. GPMC source-phase conversion uses the upstream C MPFR bridge with the upstream tolerance-selected working precision; its counter uses 30 decimal digits. Neither is end-to-end ball arithmetic.

All timing evidence comes from GitHub Actions, not the reserved Mac or the laboratory server. Whole browser requests include disposable-worker startup and WASM initialization with local HTTP/cache behavior; they exclude launching Chromium and loading the page shell. Whole native requests include process startup. Post-start native body times are also retained but should not be confused with whole-process latency. The geometric-mean browser/native comparison excludes native requests below 100 ms to reduce the startup-floor effect; coverage never excludes them. Host-to-host input rankings are not a controlled common-CPU comparison. SHA256 anchors flag frequency/load drift; raw times are never silently corrected.

Correctness evidence is separate: 125 core unit tests, 48 brute-force small weighted-CNF oracles, eight source-weight reference cases (exact Clifford, rational radians, mixed phases and 1e-400), and 24 native/browser circuit differential cases with 18 actual GPMC calls. QASM 3, invalid input, upload/download, Stop, timeout and 390px layout were exercised in Chromium. Native/WASM disagreement in the full screen must be listed, not turned into a certificate by repeated timing.

Source ledgers: README.md, NOTICE.md, manifest.json and the permanent web-mpfr-20261115 release. Complete fork sources, the original C bridge, patched counter sources, GMP/MPFR source tarballs, licenses, rebuild instructions, exact compiled assets and SHA256 records are archived there.

## Isolated browser timing protocol (revision 2)

The first screen (43621384256), and retries of its noisy batches, are excluded from performance claims. A real active-timeout audit (43624125758) found that Chromium can briefly consume CPU for asynchronous worker teardown after `Worker.terminate()`; the initial screen reused that browser and could measure its next sample during this cleanup. The numerical results remain useful checks, but its timing ratios and anchor-qualified subsets are superseded. The audit showed activity settling afterward; it did not establish a permanently running solver.

Revision 2 launches a fresh Chromium/browser page for each WASM request and awaits complete browser/server closure plus a short settling interval before the next sample. It records browser launch and cleanup separately and excludes both from request latency. This intentionally measures a cold browser-worker/cache context, rather than the initial warm-cache panel. Native and WASM samples remain serial, rotated and pinned to one core. Anchors now compare states with no open benchmark browser on either side. All original exclusions and raw data remain archived; no old timing is pooled into the isolated screen.

The final isolated screen is run43624612362:220cells/892trials, all24anchors within10% (0.939443–1.027042). Active-timeout audit43624731517 measured zero settled/post-close CPU and caught a real disabled-terminate mutant (~one busy core); its JSON is archived with the web release. The initial short-window audit recorded transient cleanup rather than proving a permanent solver leak.
